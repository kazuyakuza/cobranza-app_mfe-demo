# mfe-demo — Project Brief

**Package / Repo:** Standalone git repository (one remote only — **not** a monorepo)  
**Role:** Demo / placeholder / reference Micro-frontend (MFE) for the Company Back-office Shell  
**Target consumers:** Company Back-office Shell (during development and as living example for future MFEs)  
**Language of UI:** Spanish only (no i18n)  
**Target:** Desktop-only (same as Shell)

**Related packages (already published):**

- `@cobranza-apps/ui` — theme + ModuleHeader / ModuleContainer + core components
- `@cobranza-apps/mfe-events` — typed Shell ↔ MFE event contracts
- `@cobranza-apps/entities` — domain models (optional for this MFE; use only if needed for type examples)

## 1. Purpose

`mfe-demo` is a **real Native Federation remote** used for three things:

1. **Test harness** for the Shell while it is WIP (workspace rows, 50%/100%, collapse, fullscreen, drag & drop, persistence, multi-instance).
2. **Living reference** of how a Company MFE must implement the Shell ↔ MFE contract.
3. **Placeholder** that can appear in the Footer config so developers can add modules without waiting for real business MFEs (`mfe-clients`, `mfe-debts`, etc.).

It is **not**:

- A runtime base class / library that other MFEs must depend on
- A business domain module
- Part of the production product UI for end companies (it may stay available in non-prod environments)

**Core rules (inherited):**

- Never manipulate the DOM outside its own container.
- Never know about rows, drag-and-drop, or the workspace layout engine.
- Communicate with the Shell only via `@cobranza-apps/mfe-events` + Angular Inputs provided by the Shell host.
- Module chrome (title bar actions, drag handle) is owned by the Shell / `@cobranza-apps/ui`. This MFE only renders content inside the body area.

## 3. What the MFE must support

### 3.1 Multi-instance

The same remote can appear **multiple times** in the workspace.  
Every instance receives a unique `instanceId` (UUID generated by the Shell).

The MFE **must**:

- Filter all `shell:*` events by `instanceId` (+ usually `moduleType`)
- Include `moduleType` + `instanceId` in every `mfe:*` event it dispatches
- Keep its internal state isolated per instance (no shared singleton state across instances)

### 3.2 Inputs from Shell (host → component)

The Shell hosts the remote component and passes (at minimum):

| Input | Type | Purpose |
| ------- | ------ | --------- |
| `moduleType` | `string` | Always `'demo'` for this remote |
| `instanceId` | `string` (UUID) | Unique per workspace instance |
| `size` | `'50%' \| '100%'` | Current width fraction. You may use `short` (for `50%`) and `long` (for `100%`) instead |
| `isCollapsed` | `boolean` | Collapsed state |
| `isFullscreen` | `boolean` | Fullscreen state |
| `data` | `Record<string, unknown> \| undefined` | Opaque initial / runtime data from footer or navigation (see §3.6) |
| (optional) pixel size / minHeight related inputs | as defined by Shell | If Shell prefers Inputs over events for dimensions |

The MFE must react to changes of these Inputs (tables/charts/content should adapt when size or fullscreen changes).

### 3.3 Events — MFE → Shell (must implement)

Use helpers from `@cobranza-apps/mfe-events`. Minimum set for the demo:

| Event | When to fire | Demo behaviour |
| ------- | -------------- | ---------------- |
| `mfe:module-ready` | After first successful mount | Shell can hide skeleton |
| `mfe:update-header` | On init and when user changes title/status in the demo UI | Update title + status badge |
| `mfe:show-notification` | Button “Mostrar notificación” | Toast success / warning / error |
| `mfe:request-fullscreen` | Button “Pedir pantalla completa” | Shell switches this instance to fullscreen |
| `mfe:request-remove` | Button “Pedir quitar” (optional) | Shell removes this instance |
| `mfe:module-error` | Only if intentional error demo is triggered | Optional error path |

`mfe:request-add-module` can be demonstrated with a button that asks the Shell to add **another** `demo` instance (or a different type if the Shell already registers more remotes). When used, it may include `initialData` to pre-configure the new instance’s view (see §3.6).

Note: always review and follow lib documentation.

### 3.4 Events — Shell → MFE (must listen)

| Event | Demo behaviour |
| ------- | ---------------- |
| `shell:module-state` | Update internal display of size / collapse / fullscreen / dimensions; reflow content |
| `shell:visibility-changed` | Pause / resume heavy work if needed (demo can just log or show a badge) |
| `shell:theme-changed` | Optional; theme is global via CSS tokens — only react if demo needs to |

Always filter by `instanceId`.

Note: always review and follow lib documentation.

### 3.5 Min-height declaration

If the Shell contract supports it (Input and/or event), the demo should declare a sensible `minHeightPx` (e.g. enough for header chrome + a small form + a short table). Update it if the content changes significantly (different views may need different min-heights).

### 3.6 Configurable view mode via `data` (DemoConfig)

The Shell already transports opaque configuration through the existing channel — **no changes to `@cobranza-apps/mfe-events` are required**.

| Source | Field | Behaviour |
| -------- | ------- | ----------- |
| Shell – Footer definition | `WorkspaceModuleDefinition.config` | Copied to `data` when the instance is created |
| Shell – workspace state | `WorkspaceModule.data?: Record<string, unknown>` | Persisted / restored with the instance |
| Shell → MFE | **Input** `data` | Passed by the host component |
| `mfe:request-add-module` | `initialData?: Record<string, unknown>` | Optional; used when the demo itself requests another instance |

The Shell **does not interpret** the content of `data`. Each MFE decides the meaning.

#### Internal convention of `mfe-demo` (not part of mfe-events)

```ts
type DemoViewMode = 'table' | 'create-form' | 'profile';

interface DemoConfig {
  /** Which body content to render. Default: `'table'`. */
  view?: DemoViewMode;
  /** Optional title to push via `mfe:update-header` on init. */
  title?: string;
  /** Optional mock profile data when `view === 'profile'`. */
  profile?: Record<string, unknown>;
  /** Optional number of mock rows when `view === 'table'`. */
  tableRows?: number;
}
```

Inside the component:

```ts
@Input() data: Record<string, unknown> | undefined;

get config(): DemoConfig {
  return (this.data ?? {}) as DemoConfig;
}

get view(): DemoViewMode {
  return this.config.view ?? 'table';
}
```

#### Example Footer entries (Shell side)

```ts
{
  moduleType: 'demo',
  label: 'Demo – Tabla',
  config: { view: 'table' }
},
{
  moduleType: 'demo',
  label: 'Demo – Alta',
  config: { view: 'create-form', title: 'Alta simulada' }
},
{
  moduleType: 'demo',
  label: 'Demo – Perfil',
  config: {
    view: 'profile',
    title: 'Cliente demo',
    profile: { nombre: 'Juan Pérez', dni: '30111222', saldo: 15000 }
  }
}
```

## 4. UI content of the demo (what the user sees)

Keep it **simple, readable, and useful for debugging**.

All content lives inside the MFE container, **below** the Shell-owned ModuleHeader.

### 4.1 Common chrome (always present)

1. **Identity panel**
   - `moduleType`
   - `instanceId` (shortened + full on hover/copy)
   - Current `size`, `isCollapsed`, `isFullscreen`
   - Current `view` mode (from config)
   - Optional: reported width/height in px when Shell sends them

2. **Visual instance marker**
   - Distinct background tint or coloured left border per instance (hash of `instanceId` → colour) so multi-instance is obvious at a glance

3. **Action buttons** (use `@cobranza-apps/ui` buttons)
   - Actualizar título / estado del header (`mfe:update-header`)
   - Mostrar notificación success / warning / error
   - Pedir pantalla completa
   - Pedir quitar módulo
   - (Opcional) Pedir agregar otra instancia `demo` (can pass different `initialData` / view)
   - (Opcional) Simular error (`mfe:module-error`)

4. **Data payload viewer**
   - Pretty-print of the raw `data` Input (if present) — useful for debugging config

5. **Event log (local)**
   - Last N events received / sent for this instance (helps debugging Shell integration)

### 4.2 View-specific body content

Rendered according to `config.view` (default `'table'`):

| `view` | Content |
| -------- | --------- |
| `'table'` | Placeholder table / list that reflows with size. Use `config.tableRows` (or a sensible default) for the number of mock rows. Short text explaining current size mode. Optional static chart placeholder to verify overflow behaviour. |
| `'create-form'` | Simulated fixed create form (not real, no API). Typical fields: nombre, documento, email, etc. Buttons that only show notifications or update header (no real submit). Content must remain usable at 50% (short mode) and 100% (long mode). |
| `'profile'` | Read-only profile / detail view (ficha). Show key-value list from `config.profile` (or sensible mock defaults if absent). Looks like a client profile card / listado de información. |

Base the view types in entities defined in `@cobranza-apps/entities`.

Spanish labels only.

**Do not** re-implement ModuleHeader, drag handle, size toggle, collapse, remove, or fullscreen chrome — those belong to the Shell / UI lib.

## 5. Federation & hosting expectations

### 5.1 Exposed entry

Expose a single bootstrap component (or route entry) that the Shell can load dynamically, e.g.:

- Remote name: `mfe-demo`
- Exposed module: `./Component` (or the name agreed with Native Federation config of the Shell)

The component must be standalone and accept the Inputs listed in §3.2.

### 5.2 Development modes

1. **Standalone preview**  
   The app can run alone (`ng serve`) with a minimal local host page that simulates Shell Inputs and listens to `mfe:*` events (useful for UI work without the full Shell). The preview host should allow selecting / injecting different `DemoConfig` values (e.g. buttons or a small selector for `view`).

2. **Loaded by Shell**  
   Primary mode: Shell loads the remote via Native Federation and injects it into the workspace / fullscreen outlet. Different Footer entries (or `initialData`) drive the different views.

### 5.3 CORS / public path

Configure federation public path so the remote works when Shell and remote run on different origins/ports in local dev. Document the expected ports in the README.

## 6. Out of scope

- Business domain logic (clients, debts, bank statements, etc.)
- Real BFF / API calls (Phase 0 = frontend-only; mocks only if needed)
- Auth / login (owned by `mfe-auth` + Shell)
- Workspace layout, drag-and-drop, persistence (Shell)
- Becoming a shared library that other MFEs import
- Mobile layout
- i18n
- Production branding for company end-users (this is a developer tool / placeholder)
- Changes to `@cobranza-apps/mfe-events` for DemoConfig (keep `data` / `initialData` as opaque `Record<string, unknown>`)
